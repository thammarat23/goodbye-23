## สาเหตุหลัก: ยามมีทางออกที่ "เงียบตลอดกาล"

ใน `watch_once()` บรรทัดแรก ๆ:

```python
pend = pending_count()      # อ่าน _scan_queue.json
if pend < 0:
    log("⛔ คิวพัง — ไม่ปลุกจนกว่าจะกู้คิวเสร็จ")
    return                  # ← จบรอบ ไม่ kill ไม่ restart ไม่ทำอะไรเลย
```

`pending_count()` คืน `-1` เมื่อ **parse `_scan_queue.json` ไม่ผ่าน** (ไฟล์พัง/เขียนไม่จบ)
พอเข้าเคสนี้ ยามจะ **วนลูปเขียน log ทุก 2 นาทีไปเรื่อย ๆ โดยไม่ปลุก worker เลย** —
จากข้างนอกดูเหมือนยามยังทำงานดี (log ขยับตลอด) แต่จริง ๆ มันไม่ได้ทำอะไรมา 7 วัน

### หลักฐานที่ตรงกันทุกจุด

| หลักฐาน | ตรงกับอาการนี้ยังไง |
|---|---|
| `_scan_queue.json` แก้ล่าสุด 30 ส.ค. 18:48 | คิวหยุดถูกเขียนตั้งแต่ตอนนั้น |
| `_worker1/2.log` หยุด 30 ส.ค. 18:55 | worker ตายหลังคิวหยุด ~7 นาที |
| `_scan_pids.json` ts = **30 ส.ค. 18:34** | `start_auto()` ไม่เคยถูกเรียกอีกเลยตั้งแต่นั้น = **ยามไม่เคย restart ใครใน 7 วัน** |
| `_watch.log` โต 1.76 → 2.09 MB (~119 ไบต์/รอบ ทุก 120 วิ) | ยามยังวนลูปเขียน log ทุกรอบ แต่เป็นบรรทัดเดิมซ้ำ ๆ |

## สาเหตุรอง (ทำให้ "เงียบบ่อย" แม้คิวไม่พัง)

1. **`STUCK_MIN = 120`** — ยามยอมให้คิวไม่ขยับได้ถึง **2 ชั่วโมง** ก่อนจะ restart
   ทุกครั้งที่ worker ค้าง = เสียเวลาเปล่าอย่างน้อย 2 ชม.

2. **`pid_alive()` เช็คแค่ว่า PID ยังมีอยู่** — โปรเซสที่ค้าง (hang) นับเป็น "ยังไม่ตาย"
   ตัวจับค้างจริง ๆ มีแค่ `is_stuck()` ที่อ่าน `_scan_queue.json` — ซึ่งเป็นตัวเดียวกับที่ถูกปิดไปตอนคิวพัง

3. **PID ซ้ำ (Windows recycle PID)** — ถ้าโปรเซสอื่นได้ PID เดิม `pid_alive()` จะคืน True ตลอดไป

4. **ตัววัดความคืบหน้ามีทางเดียว** — ผูกกับ `_scan_queue.json` ล้วน
   ไม่ได้ดู mtime ของ `_worker*.log` หรือจำนวนไฟล์ใน `_ocr/` เป็นตัวสำรอง

- ถ้าเจอ `✅ ตัวสแกน OK` ซ้ำ ๆ → แปลว่า `pid_alive` โดนหลอก (PID ซ้ำ/โปรเซสค้าง)

เอาไฟล์ backup ล่าสุดที่ parse ผ่าน copy ทับ `_scan_queue.json`

### 3. อุดรูในตัวยาม (แก้ที่ต้นเหตุ ไม่ให้เงียบซ้ำ)

- เคส `pend < 0` **ห้ามเงียบ** — ให้กู้จาก backup อัตโนมัติ หรืออย่างน้อยเขียนไฟล์ธง `_ALERT.txt` ไว้ให้เห็น
- ลด `STUCK_MIN` จาก 120 → 20-30 นาที
- เพิ่มตัวจับค้างสำรองที่ไม่พึ่งคิว: ถ้า mtime ของ `_worker1.log` ไม่ขยับเกิน N นาที → kill + restart
- `pid_alive()` ควรเทียบเวลาเริ่มโปรเซสกับ `ts` ใน `_scan_pids.json` ด้วย กัน PID ซ้ำ
